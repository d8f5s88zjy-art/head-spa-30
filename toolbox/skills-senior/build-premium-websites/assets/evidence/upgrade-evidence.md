## Task applications

A fresh-context application of the earlier skill to a €4,000 service-site brief already produced a bounded photo-led plan, CMS handling, booking and targeted performance checks. This is evidence that the starting skill had useful behavior; do not describe it as failing just to inflate the upgrade.

The upgraded skill was independently applied to the same raw brief. It produced three explicit composition alternatives, a selected direction, concrete scene phases, CMS resilience cases and evidence classes tied to actual checks. This was a plan application, not a built client website or measured conversion result.

A third fresh-context application addressed product-gallery integration and exposed an ownership gap: suppressing stale commits does not by itself dispose a successfully loaded stale model. The original loader stays narrow; `owned-selection.mjs` now makes ownership transfer explicit through synchronous `claim()`. Stale, cancelled, late and failed-before-claim values are discarded; the application owns values after claim and must release previous/current models. A later cleanup error cannot cause the wrapper to discard the newly owned value. Five local regression tests cover these branches, and an independent source review found no material issue within that contract. GPU disposal remains unverified.

The independent integration exercise also executed seven in-memory ownership checks on its proposed wrapper; those exploratory checks are not included in the final bundled total of **41 tests (15 Python + 26 Node)**. Three initial task applications plus one targeted follow-up review were used in this upgrade. Task applications are not controlled statistical evidence of a multiplier.
