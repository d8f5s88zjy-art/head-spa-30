## 1. Route the scope

Classify the actual request before creating work. For a small fix inspect the affected component, preserve the established direction, change it, and check the affected path. Do not run a whole research programme. For a complete website use the sequence below. For research/skill maintenance produce reusable knowledge and bounded studies; do not launch an unrelated client build.

Use the installed project workflow for persistence and deployment. Existing approval remains valid within scope. A design review checkpoint means inspect and correct your own work; it does not automatically mean pause for user approval.

Read `assets/templates/project-brief.json` and adapt it from known facts. Run `python scripts/studio.py plan BRIEF.json` to obtain a deterministic starting plan, capability warnings and required check IDs. This is an original heuristic assistant, not a feasibility guarantee or market quotation. Reconcile its output with the actual project; do not let it silently override the user.

## 2. Make decisions reviewable

Produce a compact decision record with these fields:

| Decision | Required specificity |
|---|---|
| Audience and action | One real visitor job and a real destination |
| Facts | Source, verification date, owner; explicitly mark unknowns |
| Art direction | Dominant subject, layout relationship, media language, typography roles |
| Distinctive mechanism | One repeated visual/motion motif and its narrative reason |
| Media | Existing originals, derivative needs, rights and missing assets |
| Structure | Ordered visitor questions, content that answers them, action at the decision point |
| Motion | Trigger, phase boundaries, ownership, reversal, interruption and fallback |
| Technology | Reused stack, exact dependency versions, reason for any new package |
| Constraints | Time, agreed scope, provisional transfer/render budgets, device sample |
| Acceptance | Relevant check IDs and concrete observable result |

Replace “make it premium” with an inspectable relationship: a large authentic close-up paired with compact factual copy; one accent used for actions; a recurring crop or framing motif; stable pricing; asymmetric rhythm across sections. Do not require a particular style for every client.

## 3. Execute in vertical slices

1. **Baseline:** inspect the full existing journey, available media and current build. Capture current screenshots and real faults when tools permit. Do not invent a before score.
2. **Still composition:** make hero, proof and decision sections readable at desktop and narrow widths. Set type, spacing and crop before motion. Correct clipping and weak hierarchy now.
3. **Functional slice:** wire one actual destination end to end. Keep this usable if every decorative module fails. If backend authority is absent, label the prototype honestly.
4. **Signature slice:** implement one complete scene with loading, reverse input, reduced motion and teardown. Evaluate it before multiplying it across the site.
5. **Content slice:** exercise the real CMS with a long title, missing optional photo, reordered items and an unpublished record. Restore fixture edits in the authorized test environment.
6. **Whole composition:** review actual scroll rhythm and stable frames, then check relevant behavior. Fix the three highest-impact defects; repeat only checks affected by those changes.
7. **Delivery:** preserve editable sources, pinned dependencies, content model, rollback route and verified limits. Publication is a distinct action under the existing authorization.

For each slice use `intent → implementation → observation → correction`. A plan or screenshot is not evidence that an integration works.

## 4. Ten improvement tracks

Use these tracks to target a requested “10× improvement”; they are dimensions, not a measured multiplier.

| Track | Deliverable | Observable improvement |
|---|---|---|
| 1. Direction | Three distinct compositional candidates; selected reason | Recognizable hierarchy and specific visual language |
| 2. Section design | Content-specific layout recipes | Different information receives appropriate treatment |
| 3. Continuity | Scene boundaries and ownership | Reverse/reload/skip gives coherent state |
| 4. Assets | Source and derivative manifest | Correct crop, real provenance, bounded memory |
| 5. Performance | Measured bottleneck and targeted correction | Faster response or less work under stated conditions |
| 6. Mobile/accessibility | Recomposition and operable fallback | Same primary job remains possible |
| 7. Content/data | Schema, editing and failure contracts | Changes do not destroy layout or truth |
| 8. Engineering | Stable state ownership and integration seams | Safe change and reproducible build |
| 9. Acceptance | Evidence ledger tied to a build | Failed/missing checks cannot be presented as passed |
| 10. Learning | Independent task application and observed correction | A reusable rule addresses a demonstrated failure |

## 5. Stop conditions

Stop optional polishing when the agreed task works, relevant defects are corrected and evidence is sufficient. Stop adding effects when they obscure the offer, disrupt navigation, damage the mobile composition or exceed a measured budget without justified benefit. Keep a blocked check as blocked; finish independent work. Do not claim literal “10×” quality, conversion uplift, universal compatibility or retraining from a skill edit.

## Senior decision gate

- **Decision:** Scale process to the actual request and isolate the weakest assumption.
- **Deliverable:** A scoped plan and reviewable vertical slices.
- **Verification:** Observe each slice before propagating its pattern.
