# 005 — Discovery a overiteľné požiadavky

Use when a brief names a style, price or technology without describing the visitor's task. Resolve known context before asking the user to repeat it.

## Decide

Identify who uses the site, what action matters and what evidence must precede that action. Classify a request as a feature, quality attribute, constraint or preference. “Cinematic” is a visual intention; “booking survives a failed video load” is an acceptance condition. Record assumptions with consequences rather than filling gaps with invented facts.

## Execute

Inspect the current pages, available content, real destination links, CMS ownership and established stack. Convert each important request into a small behavior statement: actor, precondition, action, observable result. Include the failure that would be expensive to discover late. For a barber site, distinguish opening a provider's booking page from creating a confirmed reservation.

Maintain a compact scope table with required, optional and excluded work. Set the first useful release and identify inputs that constrain it. Use a short prototype only to resolve a specific uncertainty, such as whether a portrait photograph can carry the proposed composition. Preserve evidence of the answer and discard throwaway complexity.

## Verify

Walk the proposed journey using supplied facts. Check that each required feature has a content/data owner and a check. If a missing backend prevents confirmation, label that dependency instead of promising a real submission. Challenge conflicting requirements: a large interactive simulation on a tight mobile budget needs a fallback or narrower scope.

## Deliver

Produce a brief containing the visitor job, verified facts, requirements, constraints, unknowns, scope boundary and acceptance examples. Keep the brief as short as the project permits; discovery is complete when it enables responsible execution, not when every imaginable question has been asked.
